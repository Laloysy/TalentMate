## 2. 接口限流（P0）

新增 `server/middleware/rateLimit.js`，基于 `express-rate-limit`。

| 限流器 | 作用范围 | 窗口 / 额度 | 说明 |
|---|---|---|---|
| `globalLimiter` | 全站 | 15 分钟 / 600 | 宽松兜底，只挡明显滥用与爬取 |
| `authLimiter` | 登录、注册 | 15 分钟 / 20 | 仅统计失败尝试 |
| `voiceLimiter` | `/api/voice/recognize` | 5 分钟 / 30 | 消耗腾讯云 ASR + DeepSeek 额度 |
| `mailLimiter` | `/api/mail/preview` | 5 分钟 / 60 | 服务端渲染邮件模板 |

两个关键设计：

- **登录限流只统计失败**（`skipSuccessfulRequests: true`）：正常用户反复登录不会被自己"刷满"，
  但仍然能有效拦住密码暴力破解。
- **计数键优先用 userId**，未登录才退化为 IP。同一出口 IP 后面可能有大量真实用户
  （公司网络、校园网），只按 IP 限流会误伤。未登录分支调用
  `ipKeyGenerator(req)` 而不是直接用 `req.ip`，因为后者不会把 IPv6 归一化到 /56 子网，
  攻击者换个 IPv6 地址就能绕过（这是 express-rate-limit v7+ 的明确要求）。

> 部署在 Nginx 之后，`app.js` 设置了 `app.set('trust proxy', 1)`，
> 否则 `req.ip` 会全部是 `127.0.0.1`，按 IP 的限流会失效。

## 3. 邮件 HTML 转义（P0）

**审计结论**：`renderCareEmail()`（用户可编辑的关怀邮件）**已经**对
`subject / name / body / title / start_time` 全部调用了 `escapeHtml`，
原先担心的问题在这里并不存在。

**但发现一处真实遗漏**：`sendReminderEmail()`（发送给用户自己的日程提醒邮件）
在第 56、60、64 行把 `eventTitle / startTime / reminderMinutes`
**直接插进 HTML 模板**，没有转义。事件标题是用户完全可控的字段：

```
事件标题 = <img src=x onerror=...>
→ 提醒邮件 HTML 里原样落地
```

已修复为插入前先 `escapeHtml`。

> 说明：本次也确认了 SQL 全部使用参数化查询（`?` 占位符），
> 未发现拼接用户输入的情况。

## 4. 日志脱敏（P1）

新增 `server/services/logger.js`，在写入 `console.*` 之前递归脱敏：

- 命中敏感 key（`password / secret / token / jwt / authorization / apiKey /
  privateKey / signature / SMTP_PASS / DB_PASSWORD` 等）→ `[redacted]`；
- 大字段（`body / audio / transcript / detail / notes`）→ 只记长度；
- `Error` 对象只保留 `name` 与 `message`，**不输出 stack**
  （stack 里常带连接串与内部路径）；
- 字符串里形如 `Bearer xxx` 的内容，以及独立出现的 JWT / 长 base64 串
  （云服务密钥、签名）→ 一并替换。

**同时收紧了全局错误处理**：原来把 `err.message` 直接返回给客户端，
可能泄漏数据库结构或内部路径，现已改为固定文案「服务器内部错误」，
细节只进脱敏日志。

> 迁移状态：`app.js` 已改用脱敏 logger。其余路由文件目前仍是原生
> `console.error('...', err)`，建议后续逐步替换为 `require('../services/logger')`；
> 这一步不影响功能，所以没有一次性大改以免引入风险。

## 5. 数据库业务账户（P1）

新增 `server/db/create-app-user.sql`：创建只对 `voice_calendar` 库有
`SELECT / INSERT / UPDATE / DELETE / ALTER / INDEX` 权限的 `talentmate_app` 账户。

> 保留 `ALTER` 是因为 `services/schema.js` 启动时会做「缺列则补列」的
> `ALTER TABLE`。若后续不再需要自动补列，可以去掉该项进一步收紧。

**需要在腾讯云服务器上手动执行一次**（会修改数据库权限，因此没有自动执行）：

```bash
# 1. 先修改脚本里的占位密码
vi server/db/create-app-user.sql

# 2. 执行
docker compose exec -T mysql mysql -uroot -p < server/db/create-app-user.sql

# 3. 修改 .env：DB_USER=talentmate_app / DB_PASSWORD=<新密码>

# 4. 重建并重启后端
docker compose up -d --build server
```

## 6. 未完成：日期与时区统一（P1）

**为什么没做**：这是一项涉及存储、接口、前端三层的格式变更，
且需要真机/多时区场景验证，属于独立一轮工作。在没有充分验证的情况下
直接改时间语义，风险高于收益（可能出现日程整体偏移）。

**现状与风险**：

- 数据库连接设了 `dateStrings: true`（`server/db.js`），DATETIME 以字符串原样返回；
- 前端用 dayjs 解析「本地时间字符串」，两端都假设同一时区；
- 因此**当服务器时区与用户时区不一致时，日程时间会偏移**。
  当前服务器（腾讯云）与主要用户都在 UTC+8，所以暂时不暴露问题。

**建议做法**（下一轮）：

1. 存储统一用 UTC，接口输出 ISO 8601 带时区（如 `2026-10-07T02:00:00Z`）；
2. 前端按设备时区渲染；
3. 明确「全天事件」的规则（用 DATE 而非 DATETIME，避免时区换算）；
4. 统一开始/结束时间的边界语义（当前接口是闭区间
   `start_time >= ? AND start_time <= ?`，前端必须传 `"YYYY-MM-DD 00:00:00"`
   才正确，这个隐式约定本身就该改掉）。
