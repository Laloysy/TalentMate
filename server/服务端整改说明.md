## 2. 接口限流（P0）

新增 `server/middleware/rateLimit.js`，基于 `express-rate-limit`。

| 限流器 | 作用范围 | 窗口 / 额度 | 说明 |
|---|---|---|---|
| `globalLimiter` | 全站 | 15 分钟 / 600 | 宽松兜底，只挡明显滥用与爬取 |
| `authLimiter` | 登录、注册 | 15 分钟 / 20 | 仅统计失败尝试 |
| `voiceLimiter` | `/api/voice/recognize` | 5 分钟 / 30 | 消耗腾讯云 ASR + DeepSeek 额度 |
| `mailLimiter` | `/api/mail/preview` | 5 分钟 / 60 | 服务端渲染邮件模板 |

两个关键设计：

- **登录限流只统计失败**（`skipSuccessfulRequests: true`）：正常用户反复登录不会被自己"刷满"，
  但仍然能有效拦住密码暴力破解。
- **计数键优先用 userId**，未登录才退化为 IP。同一出口 IP 后面可能有大量真实用户
  （公司网络、校园网），只按 IP 限流会误伤。未登录分支调用
  `ipKeyGenerator(req)` 而不是直接用 `req.ip`，因为后者不会把 IPv6 归一化到 /56 子网，
  攻击者换个 IPv6 地址就能绕过（这是 express-rate-limit v7+ 的明确要求）。

> 部署在 Nginx 之后，`app.js` 设置了 `app.set('trust proxy', 1)`，
> 否则 `req.ip` 会全部是 `127.0.0.1`，按 IP 的限流会失效。

## 4. 日志脱敏（P1）

新增 `server/services/logger.js`，在写入 `console.*` 之前递归脱敏：

- 命中敏感 key（`password / secret / token / jwt / authorization / apiKey /
  privateKey / signature / SMTP_PASS / DB_PASSWORD` 等）→ `[redacted]`；
- 大字段（`body / audio / transcript / detail / notes`）→ 只记长度；
- `Error` 对象只保留 `name` 与 `message`，**不输出 stack**
  （stack 里常带连接串与内部路径）；
- 字符串里形如 `Bearer xxx` 的内容，以及独立出现的 JWT / 长 base64 串
  （云服务密钥、签名）→ 一并替换。

**同时收紧了全局错误处理**：原来把 `err.message` 直接返回给客户端，
可能泄漏数据库结构或内部路径，现已改为固定文案「服务器内部错误」，
细节只进脱敏日志。

> 迁移状态：`app.js` 已改用脱敏 logger。其余路由文件目前仍是原生
> `console.error('...', err)`，建议后续逐步替换为 `require('../services/logger')`；
> 这一步不影响功能，所以没有一次性大改以免引入风险。

## 5. 数据库业务账户（P1）

已在生产服务器上创建并启用：账户 `talentmate_app`，只对 `voice_calendar` 库拥有
`SELECT / INSERT / UPDATE / DELETE / CREATE / REFERENCES / INDEX / ALTER` 权限，
**没有** `DROP`、`GRANT OPTION`、`CREATE USER`、`SUPER`、`FILE`，也无法访问 `mysql` 系统库。

> 为什么需要 `CREATE` / `REFERENCES`：`services/schema.js` 启动时会执行
> `CREATE TABLE IF NOT EXISTS`（含外键）。只给 `ALTER` 时日志会报
> `[Schema] Failed to ensure schema: CREATE command denied to user ... for table 'contacts'`，
> 应用功能不受影响但会留下误导性的启动错误。
> 只给 `ALTER` 时还会有一个真实风险：将来新增表时应用无法自建，需要人工迁移。

脚本见 `server/db/create-app-user.sql`。在已有部署上启用时注意两点：

1. **先验证再切换**：先用业务账户实际连一次库并读一张表，确认无误后再改 `.env`；
2. **切换 `.env` 后 root 密码就「不在 `.env` 里了`**：
   `docker-compose.yml` 用 `${DB_PASSWORD}` 作为 `MYSQL_ROOT_PASSWORD`，
   一旦把 `DB_PASSWORD` 换成业务账户密码，就再也无法用 `.env` 登 root。
   本机还发现容器的 `MYSQL_ROOT_PASSWORD` 与 MySQL 实际 root 账户并不匹配
   （root 登录被拒），最终是用「切换前的 `.env` 备份」里的原密码完成授权的。

**回滚方式**：

```sql
DROP USER 'talentmate_app'@'%';
```

然后把 `.env` 的 `DB_USER` / `DB_PASSWORD` 改回原账户并重启 server 容器。

## 6. 生产部署说明（重要）

生产服务器 `/root/talentmate` **没有安装 git**，也没有 `client/android`，
代码是整包上传的。另外这台机器只有 **1.7GB 内存**，因此部署方式有硬性约束。

### 6.1 绝不要在服务器上构建客户端

在容器内跑客户端构建（`pnpm install` 数百个包 + Vite 打包）会把内存打满，
导致 `sshd` / `nginx` 无法 fork，**整机失联**（本次已实际发生一次）。
恢复只能靠腾讯云控制台重启实例。

根因修复：已为该机器添加 **2GB swap**（写入 `/etc/fstab`，`vm.swappiness=10`）。

### 6.2 正确的部署流程

```bash
# 本地：构建前端
cd client && pnpm run build

# 打包（排除依赖、git、android 等服务器不需要的内容）
tar -czf deploy.tgz --exclude=./.git --exclude=./node_modules \
  --exclude=./client/node_modules --exclude=./server/node_modules \
  --exclude=./client/android --exclude=./server/uploads .

# 上传并解包（不会覆盖 .env）
scp -i <key> deploy.tgz root@49.232.160.212:/tmp/
ssh -i <key> root@49.232.160.212 \
  "cd /root/talentmate && tar -xzf /tmp/deploy.tgz"

# 服务器：只构建服务端，直接使用本地已构建的 client/dist
ssh -i <key> root@49.232.160.212 \
  "cd /root/talentmate && docker compose build --build-arg PREBUILT_CLIENT=1 && docker compose up -d"
```

### 6.3 两个容易踩的坑

1. **pnpm 版本必须固定**：Dockerfile 用 `npm install -g pnpm` 会装到当时最新版
   （实测 10.34.1），它对「被忽略的安装脚本」直接报 `ERR_PNPM_IGNORED_BUILDS` 并失败，
   而本地 pnpm 10.24 只是警告。已在 Dockerfile 中固定 `pnpm@10.24.0`。
2. **`.dockerignore` 不能排除 `client/dist`**：否则 `PREBUILT_CLIENT=1` 会报
   `failed to calculate checksum ... /client/dist: not found`。
   另外 `dist`（不带斜杠）会匹配任意层级的同名目录，必须写成 `/dist`。

### 6.4 服务器拓扑

```text
公网 49.232.160.212:80
  └─ nginx: talentmate-ip-http.conf
       ├─ /api/  → 127.0.0.1:3001 (Express)
       └─ /      → 404（有意为之：APK 只用这个 IP 调接口）

域名 sytus.cloud（TencentEdgeOne CDN 在前）
  └─ nginx: talentmate.conf (443, 自签/自有证书)
       └─ /      → 127.0.0.1:3001（Express 托管 client/dist 静态资源）
```

> 因此「用 IP 访问首页得到 404」是**预期行为**，不是故障；
> 前端页面通过域名访问，Android 端通过 IP 调 `/api/*`。

## 7. 未完成：日期与时区统一（P1）

**为什么没做**：这是一项涉及存储、接口、前端三层的格式变更，
且需要真机/多时区场景验证，属于独立一轮工作。在没有充分验证的情况下
直接改时间语义，风险高于收益（可能出现日程整体偏移）。

**现状与风险**：

- 数据库连接设了 `dateStrings: true`（`server/db.js`），DATETIME 以字符串原样返回；
- 前端用 dayjs 解析「本地时间字符串」，两端都假设同一时区；
- 因此**当服务器时区与用户时区不一致时，日程时间会偏移**。
  当前服务器（腾讯云）与主要用户都在 UTC+8，所以暂时不暴露问题。

**建议做法**（下一轮）：

1. 存储统一用 UTC，接口输出 ISO 8601 带时区（如 `2026-10-07T02:00:00Z`）；
2. 前端按设备时区渲染；
3. 明确「全天事件」的规则（用 DATE 而非 DATETIME，避免时区换算）；
4. 统一开始/结束时间的边界语义（当前接口是闭区间
   `start_time >= ? AND start_time <= ?`，前端必须传 `"YYYY-MM-DD 00:00:00"`
   才正确，这个隐式约定本身就该改掉）。
